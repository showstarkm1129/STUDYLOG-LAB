# 出席確認の受付検知メモ

## 目的

出席確認の受付は授業中に突然始まり、開始に気づかないと出席を落とす。休み時間に眠っている場合など、画面を見ていない状況でも受付開始に気づけるようにする。

自動で出席を登録することはしない。検知して知らせるところまでが範囲で、出席確認そのものは必ず本人が押す。

## 画面の前提

- 出席確認の入口は科目トップ（`/lms/class/{classId}/`）のパンくず行の右端にある。
- このボタンは、受付の有無に関わらず常に表示される。まだ実施されていない未来の科目では表示されない。
- ボタンを押すと、コード入力欄、またはコードなしで押す受付ボタンのある画面へ進む。押しただけでは出席は確定しない。

### 実機で分かったこと（2026-09-02）

科目「簿記入門a」（`classId` 10019）で確認した実際のボタンは次のとおりだった。

```html
<button id="checkEntryBtn" class="btn btn-sm btn-info" onclick="checkAttendEntry(10019);">出席確認</button>
```

`href` がなく、`GET /lms/class/{classId}/` の応答にも含まれない。JavaScript で後から描画されている。

`checkAttendEntry()` の中身を読み取ったところ、受付状態は次の1つの問い合わせで分かることが判明した。

```js
glexa.ajax({
  action: 'glexa_modal_entry_form',
  params: { class_id: classId, is_ajax: 1 },
  withoutLoading: true,
  onSuccess: function (result) {
    if (result.data.is_accepted != '1') {
      glexa.openRemoteModal({ action: 'glexa_modal_entry_form', params: { class_id: classId } });
    } else {
      glexa.openCommonAlertModal({ title: "情報", body: "現在、新たな出席確認は行われていません" });
    }
  }
})
```

意味づけが直感と逆である点に注意する。

- `is_accepted` が `'1'` … 受付済み。新たな出席確認は行われていない。
- `is_accepted` が `'1'` 以外 … 受付がある。スタログはここで受付フォームを開く。

この問い合わせは、ボタンを押した時に「フォームを出すか、何もありませんと言うか」を決めるための確認であり、出席の登録ではない。登録はこの後に開くフォーム側で行われる。

## 確認のしかた

### 受付状態を問い合わせる（`entry`・既定）

`page-hook.js` からページ側の `glexa.ajax` を使い、上記とまったく同じ問い合わせを送って `is_accepted` だけを読む。受付フォームは開かず、コードの送信も受付の確定も行わない。

- `'1'` → 受付なし。通知しない。
- それ以外 → 受付中として通知する。値が空の場合も含む。
- 応答に `data` が無い → 不明として通知しない。

値が空の場合を受付中に含めるのは、スタログ本体の分岐が `is_accepted != '1'` だからである。空の値でスタログは受付フォームを開くので、こちらだけ黙っていると受付を取り逃がす。取り逃がし（欠席になる）は誤報（音が鳴るだけ）より明らかに損害が大きいため、判定は本体に合わせてある。

`data` が無い応答だけを不明として扱うのは、それが値の読み取りですらないためである。ログイン切れなどで想定と違う内容が返った場合がこれにあたる。記録に `unknown` が並ぶ場合はこの状態を見ている。

`glexa.ajax` を作り直さずページ側の実装をそのまま呼ぶのは、CSRF 対策などの内部処理を取りこぼさないためである。スタログのタブが開いていないと使えない。

応答は小さなJSONで、科目トップのHTMLを取得するより通信量がはるかに少ない。

### 出席確認の画面まで開いて読む（`screen`）

出席確認ボタンが普通のリンクである場合だけ使える代替手段。この学校のボタンはリンクではないため機能しない。別の学校や将来の画面変更に備えて残している。

ボタンの `href` が同一オリジンの実URLの場合だけ、その画面をGETして本文を判定する。

- `受付中` `コードを入力` `出席コード` `出席を受け付け` `ボタンを押して` `認証コード` → 受付中
- `受付していません` `受付を行っていません` `受付時間外` `受付は終了` `受付が終了` `実施されていません` `対象の授業がありません` → 受付なし
- `出席済` `受付済` `登録されました` → 出席済み（その回の監視を終了する）
- どれにも当てはまらない → 不明として扱い、通知しない

判定は受付なし・出席済みを優先する。送信は行わず、画面を表示するのと同じGETだけを使う。

### 廃止した方式

科目トップのHTMLを取得し、出席確認ボタンの署名が普段と変わったかで判断する `page` モードを最初に用意したが、実機ではボタンがHTMLに含まれないため原理的に成立しないことが分かり、削除した。あわせて、平常時の見え方を控える仕組みも不要になったため削除している。

## いつ確認するか

`attendance-watch-rules.js` が監視窓を決める。窓の外では一切通信しない。

- 対象は今日の時間割にある科目だけ。同じ科目が続く時限はひとつの窓にまとめる。
- 窓は授業開始5分前から終了10分後まで。
- 開始25分後までは60秒間隔、それ以降は180秒間隔。間隔には±25%のゆらぎを付ける。
- 1つの窓で最大40回まで。超えたら静かに諦める。
- 失敗すると5分待ち、3回続けて失敗したらその窓を放棄する。
- 受付を検知した時点、および出席済みを読み取った時点でその窓を終了する。
- 複数のスタログタブを開いていても、自動収集と同じリースで1タブだけが確認する。

実際の通信回数は、受付が授業開始直後に始まれば数回で終わる。上限に張り付いた場合でも1コマ40回である。

## 知らせかた

| 手段 | 内容 |
| --- | --- |
| バッジ | 拡張機能アイコンに「出席」と表示する。常に有効。 |
| デスクトップ通知 | Chromeの通知を出す。押すとその科目のページを開く。`notifications` の任意権限が必要。 |
| 音 | Service Worker では音を鳴らせないため、`chrome.offscreen` で音声再生専用の非表示ページを開いて3回まで鳴らす。 |
| Slack | Incoming Webhook へ送る。スマートフォンのプッシュで受け取れる。`https://hooks.slack.com/*` の任意ホスト権限が必要。連携そのものは「サービス連携」の画面で行う。開通の手順は [`docs/slack-link.md`](slack-link.md) を参照。 |
| Discord | ウェブフックへ送る。内容は Slack と同じで、両方を有効にすれば両方へ届く。`https://discord.com/*` の任意ホスト権限が必要。開通の手順は [`docs/discord-link.md`](discord-link.md) を参照。 |

通知が邪魔にならないよう、次の抑制を入れている。

- その科目のページを自分で開いて見ている場合は、バッジだけにして音を鳴らさない。
- 1つの授業回につき通知は1回まで。
- 「今日はもう鳴らさない」を押すと、その日の終わりまで監視も通知も止まる。

SlackとDiscordへ送る内容は、科目名・時限・検知時刻・科目ページのリンクだけである。成績、課題、出欠数、氏名、学籍番号は送らない。どちらの Webhook のURLも `chrome.storage.local` に保存されるため、他人と共有しないこと。画面と「記録をコピー」では、URLの先頭だけを表示して以降は伏せる。

## 状態の確認

受付がない時に何も起きないのは正常な動作だが、それだけでは動いているのか壊れているのか分からない。ダッシュボードの「出席確認の見張り」で次を確認できる。

- いま監視しているか。していない場合はその理由（授業時間外、今日の授業がない、停止中、上限に達した、など）。
- 次の監視が始まる時刻と科目。
- 今日の対象科目ごとに、平常時の見え方を記録済みかどうか。
- その授業回で最後に確認した時刻。

### 今すぐ確認

監視の時間帯でなくても、選んだ科目を1回だけ読み取って結果を表示する。スタログのタブを開いておく必要がある。

読み取りはダッシュボードからではなく、スタログのタブの中で行う。拡張機能ページから直接取得するとセッションが乗らずログイン画面が返るため、実際の監視と同じ文脈に合わせている。

表示するのは次の内容である。

- **受付状態**。`is_accepted` の生の値と、それをどう解釈したか。監視ループが使う判定そのものなので、これが正しく出れば検知は成立する。
- 出席確認ボタンを、表示中の画面と取得したHTMLのそれぞれで見つけられたか。片方にしか出ない場合、ボタンが JavaScript で描画されていることが分かる。
- ボタンが押した時に呼ぶページ側の関数の中身。どこへ何を問い合わせているかを読むためのもので、実行はしない。
- ボタンがリンクである場合は、その画面の判定結果と文言の抜粋。抜粋には氏名や学籍番号が含まれる場合があるため、画面に表示するだけで保存もコピーもしない。

### 通知を試す

設定した知らせ方で、テスト用の通知を1回送る。デスクトップ通知・音・Slackの経路が実際に届くかを、受付を待たずに確認できる。テストではバッジを残さず、記録も残さない。

## 記録

判定のたびに、時刻・科目・判定結果・署名が変わったかどうかを最大60件まで端末内へ残す。コードの値、画面本文、認証情報は保存しない。ダッシュボードの「出席確認の見張り」からコピーでき、検知条件を調整する時の材料にする。

## 予行演習

受付が実際に始まるのは授業中だけなので、それ以外の時間に本番の動きを確かめる手段を用意した。ダッシュボードの「受付中として予行演習」がそれにあたる。

- 受付状態の問い合わせは本物を送る。ここで失敗するなら本番でも失敗する。
- 返ってきた答えは表示するが、判定だけを受付中に差し替えて、本番と同じ通知経路を一度だけ通す。
- 通知の科目名には `【予行演習】` を付ける。本物の受付と見分けがつかないと、かえって危険なため。
- 見張りの記録には検知も通知済みも書かない。書いてしまうと、その時間帯の本物の受付を「もう知らせた」と誤認して取り逃がす。記録には `rehearsal` として1件だけ残る。
- その科目のページを自分で開いている場合は、本番と同じ扱いで音とデスクトップ通知を止める。鳴りかたを確かめたい時は別のタブを前に出す。
- 「今日はもう鳴らさない」で停止中の場合は鳴らさず、その理由を表示する。

サーバ側に受付中の状態を作ることはできない。作れるのは判定の差し替えまでであり、受付中に `is_accepted` が実際にどの値になるかは、これでは分からない。

## 未解決の課題

受付が実際に始まっている最中の応答をまだ観測していない。次の授業で確認する。

- 受付中の `is_accepted` が実際にどの値になるか。判定はスタログ本体の分岐をそのまま写しているので、どの値であっても受付中と読めるはずだが、実物を一度は見ておきたい。
- 受付中で、かつ自分が既に出席を済ませた後の値がどうなるか。`'1'` に戻るなら、二重通知は自然に止まる。
- 応答が取れない場面がどの程度あるか。記録に `unknown` が並ぶ場合は判定を見直す。

残っている懸念として、この問い合わせ自体をサーバ側が「フォームを開いた」として記録している可能性は否定できない。ただし、これは学生が出席確認ボタンを押した時とまったく同じ問い合わせであり、押しただけでは出席が確定しないことは実機で確認済みである。
